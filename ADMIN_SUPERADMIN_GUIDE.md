## Инструкция для администратора (Admin)

- **Источник истины:** поле `ID` в базе Access (`tblKartei.ID`) должно совпадать с `Kartei!AV`. Все сопоставления делаются по этому полю.
- **Открытие файла:** при `Workbook_Open` загружаются данные из `tblKartei`, затем накладываются pending/declined из `pre_tblKartei`/`decl_tblKartei`. После наложения формируется `Kartei_Original`.

- **Статусы на листе `Kartei`:**

  - `BA="PENDING"` (колонка 53) + голубая заливка `A` — запись из `pre_tblKartei`, ждёт решения Суперадмина.
  - `BA="DECLINED"` + алая заливка `A` — запись из `decl_tblKartei`, нужна ручная работа через инструмент DeclinedOverview.
  - Если один ID есть и в pre*, и в decl* — приоритет decl\_, появляется предупреждение.

- **Роли:** `J1` определяет роль. Operator ограничен, Admin — без ограничений Operator’а. Operator не может менять прошедшие месяцы и строки AU="SEPA". Все попытки SEPA‑правок откатываются при синхронизации с сообщением.

- **Редактирование и история:** любые изменения в месяцах U–AF и полях F/J/O пишутся в историю AZ. Для прошлых месяцев у Admin добавляется префикс `Ruck:`; Notitzen обязательно для изменений. При отмене окна Notitzen обновление строки и запись в базу отменяются.

- **Синхронизация (`CompareAndSyncKartei`):**

  - Изменения делятся на **safe** (идут в `tblKartei`) и **risky** (идут только в `pre_tblKartei`). Новые ID всегда считаются safe.
  - **Политика риска (TRACKED_FIELDS):** Изменения в протоколируемых полях (которые записываются в историю AZ) считаются рискованными. Изменения в непротоколируемых полях — безопасными. Это гарантирует, что все pending-записи попадут на лист `GrossGeschichte` для валидации.
    - Протоколируемые поля: A (FamilyID), B (Parent), D (Child), E (Birthdate), F-I (Address, Phone, Mobile, Email), J (Subject1), M (Price1), O (Subject2), R (Price2), U-AF (Months 1-12), AK-AM (Extra1-3).
    - Непротоколируемые поля (изменения в них безопасны): C, K-L, N, P-Q, S-T, AG-AJ, AN-AT, AW-AY и др.
  - **Работа с PENDING записями:**
    - Admin может исправлять PENDING записи напрямую на листе `Kartei`.
    - При синхронизации изменения запишутся в `pre_tblKartei` (обновятся), статус останется `BA="PENDING"`.
    - Будет запущена процедура Notitzen для добавления комментария к истории.
    - При отмене Notitzen изменения для данной записи пропускаются.
  - **Работа с DECLINED записями:**
    - Admin может исправлять DECLINED записи напрямую на листе `Kartei` (без обязательного использования DeclinedOverview).
    - При синхронизации изменённых DECLINED записей:
      - Запускается процедура Notitzen для добавления комментария.
      - После подтверждения запись автоматически перемещается из `decl_tblKartei` в `pre_tblKartei`.
      - Статус на `Kartei` меняется с `BA="DECLINED"` на `BA="PENDING"`.
      - Заливка колонки `A` меняется с алой на голубую.
      - Запись удаляется из `decl_tblKartei`.
    - При отмене Notitzen изменения для данной записи пропускаются, статус остаётся DECLINED.
  - После синхронизации выводится сводка с подсчётом safe/risky/pending/declined записей.

- **Работа с отклонёнными:**

  - Запустите `ShowDeclinedOverview` для построения листа `DeclinedOverview`.
  - Лист будет создан сразу после листа `Kartei` для удобства навигации.
  - В ячейке U1 (в шапке) размещена кнопка **"Apply Fixes"** для быстрого запуска процедуры исправления.
  - Заголовки и ширина колонок совпадают с соответствующими колонками на листе `Kartei`.
  - Колонка U показывает только последний комментарий отклонения (Decl_n с максимальным n), а не всю историю.
  - Колонка T показывает количество отклонений для данной записи.
  - Применён AutoFilter для удобной фильтрации данных.
  - Внесите корректировки одним из двух способов:
    - **На листе `DeclinedOverview`** — изменения в этом листе имеют приоритет.
    - **На листе `Kartei`** — если на `DeclinedOverview` изменений не было, будут использованы данные из `Kartei`.
  - Выполните `ApplyDeclinedFixes` (нажмите кнопку **"Apply Fixes"** или запустите макрос вручную):
    - Система определит для каждого ID источник исправленных данных (DeclinedOverview или Kartei).
    - Если данные изменились на `DeclinedOverview`, они сначала копируются в соответствующую строку на `Kartei`.
    - Исправленные записи переносятся из `decl_tblKartei` в `pre_tblKartei`.
    - На `Kartei` устанавливается статус `BA="PENDING"` и голубая заливка колонки `A`.
    - ID удаляется из `decl_tblKartei`.
    - Лист `DeclinedOverview` автоматически удаляется после обработки (в любом случае, даже если записей не было).
  - При закрытии файла Админа лист `DeclinedOverview` также автоматически удаляется (если существует), чтобы каждая сессия начиналась с чистого листа.

- **Быстрый просмотр комментария отклонения:**
  - Для быстрого просмотра последнего комментария Суперадмина по отклонённой записи используйте процедуру `ShowLastDeclineCommentForCurrentRow`.
  - Встаньте на строку с отклонённой записью (статус `BA="DECLINED"`) на листе `Kartei` и запустите макрос.
  - Поддерживаются оба формата записи отклонений:
    - **Legacy формат:** `Decl_n: Was(); Is(...)`
    - **Новый формат:** `DCL(n->...)`
  - В окне сообщения отобразится текст из последнего блока отклонения с максимальным номером n из истории (колонка AZ).
  - Если строка не отклонена или не содержит блоков отклонений, будет показано соответствующее информационное сообщение.

## Инструкция для суперадмина (Superadmin)

- **Источник данных:** pending‑записи из `pre_tblKartei` (ID = AV) импортируются на лист `Kartei` файла Суперадмина.
- **Загрузка pending:** выполните `valid_ImportPending.LoadPendingChangesFromPre` (или `valid_ApproveFlow.LoadPendingChanges`) — подтянутся все pending по ID, затем построится лист `GrossGeschichte` для анализа истории.
- **Автоматическое форматирование:** после загрузки месячные колонки U-AF (21-32) автоматически форматируются как числовые с двумя десятичными знаками и корректным разделителем (запятая или точка в зависимости от системных настроек Excel).

### Структура листа GrossGeschichte (обновлено)

Новая структура столбцов обеспечивает компактный вид и располагает столбец Decision (AC) ближе к данным:

| Столбец | Поле            | Описание                            |
| ------- | --------------- | ----------------------------------- |
| A       | FamilyID        | Идентификатор семьи                 |
| B       | Parent          | Имя родителя                        |
| C       | Child           | Имя ребёнка                         |
| D       | Birthdate       | Дата рождения (текст dd.mm.yyyy)    |
| E       | Address         | Адрес                               |
| F       | Phone           | Телефон (текст)                     |
| G       | Mobile          | Мобильный (текст)                   |
| H       | Email           | Email                               |
| I       | Subject1        | Предмет (месяцы 1-6)                |
| J       | Price1          | Цена Subject1                       |
| K       | Subject2        | Предмет (месяцы 7-12)               |
| L       | Price2          | Цена Subject2                       |
| M-X     | Jan-Dez         | Месячные начисления (числовой 0.00) |
| Y-AA    | Extra1-3        | Дополнительные предметы             |
| AB      | Comments        | Комментарий изменения               |
| AC      | Decision        | Approved / Declined                 |
| AD      | Decline Comment | Причина отклонения                  |
| AE      | RecordID        | Скрытый (внутренний ID записи)      |

Каждое событие изменения занимает 3 строки:

- **Строка N** (War): Старые значения до изменения
- **Строка N+1** (Ist): Новые значения после изменения
- **Строка N+2**: Серый разделитель

Изменённые ячейки в строке "Ist" подсвечены светло-розовым цветом.

### Форма транспонирования (geschichteForm)

Для детального просмотра одной записи используйте форму транспонирования:

1. Перейдите на лист **GrossGeschichte**
2. Кликните на любую ячейку записи, которую хотите просмотреть
3. Запустите макрос `ShowTransposeForm`
4. Будет создан временный лист `geschichteForm` с вертикальной раскладкой:
   - Столбец A: Названия полей
   - Столбец B: Старые значения (War)
   - Столбец C: Новые значения (Ist)
5. Выберите решение в строке "Decision" (Approved/Declined)
6. При отклонении введите комментарий в строке "Decline Comment"
7. Нажмите кнопку **"Apply & Close"**
8. Решение сохраняется в GrossGeschichte, временный лист удаляется

**Преимущества формы:**

- Все поля видны на одном экране без горизонтальной прокрутки
- Удобное сравнение старых и новых значений
- Изменённые поля подсвечены
- Быстрый ввод решения с валидацией

### Выбор режима отображения

- При запуске `GrossGeshichteMachen` система предложит выбрать режим через диалоговое окно:
  - **Mode A (YES):** Показать все события в указанном диапазоне дат
  - **Mode B (NO):** Показать только последнее изменение для каждого ID в указанном диапазоне дат
- В **Mode B** для каждого ID отображается только событие с максимальной датой; если несколько событий имеют одинаковую максимальную дату, выбирается последнее по порядку в истории
- В **Mode A** отображаются все события для всех ID в диапазоне дат

### Просмотр истории

- `GrossGeschichte` показывает события по каждому ID (месяцы, Address/Subject1/Subject2, Decl_n) в выбранном режиме
- `Geschichte` можно вызывать на активной строке для детального просмотра отдельной записи

### Принятие решения

**Способ 1 - Прямая разметка:**

- На `GrossGeschichte` пометьте для нужных строк `Decision` (колонка AC) = Approved или Declined
- Для Declined укажите комментарий в колонке AD; если не указан, система запросит его интерактивно

**Способ 2 - Форма транспонирования:**

- Выберите запись на GrossGeschichte
- Запустите `ShowTransposeForm`
- Введите решение в форме
- Нажмите "Apply & Close"
- Повторите для других записей

### Обработка конфликтующих решений (Mode A)

- Если для одного ID присутствует несколько блоков (несколько событий), только решение из последнего события (с максимальной датой и последнее в порядке) будет применено
- Система автоматически отфильтрует дубликаты и применит единственное решение на ID
- В **Mode B** конфликты исключены, так как для каждого ID отображается только один блок

### Применение решений

- Запустите `valid_ApproveFlow.SyncDecisions`.
- Approved: запись (по ID) переносится из `pre_tblKartei` в `tblKartei` и удаляется из `pre_`.
- Declined: запись (по ID) переносится из `pre_tblKartei` в `decl_tblKartei` с новым `Decl_n` и удаляется из `pre_`.
- Гарантируется, что каждый ID попадёт только в одну категорию (approved или declined), без дублирования

### Доступные макросы

| Макрос                 | Описание                                             |
| ---------------------- | ---------------------------------------------------- |
| `LoadPendingChanges`   | Загрузить pending и сгенерировать GrossGeschichte    |
| `GrossGeshichteMachen` | Сгенерировать/перегенерировать отчёт GrossGeschichte |
| `ShowTransposeForm`    | Открыть форму транспонирования для текущей записи    |
| `SyncDecisions`        | Обработать все решения Approved/Declined             |
| `CloseTransposeForm`   | Закрыть форму транспонирования без сохранения        |

- **Инвариант ID:** после любых действий проверяйте, что AV на листе совпадает с ID в `tblKartei/pre_tblKartei/decl_tblKartei`; все операции сопоставляют строки по этому полю.
