## 0. Цель и ограничения

**Цель**: новая модель прайса на основе категорий/групп, которая вычисляет помесячные базы и начисления, не ломая существующие данные.

**Инвариант**: `months_mode=AUTO` + `base_amounts` = "история баз по месяцам". Нельзя молча переписывать прошлые месяцы.

**PriceOption (вариант B)**: `PriceOption` остаётся и продолжает работать для **некатегорийных** дисциплин. Для дисциплин, привязанных к категории, ценообразование идёт через новую логику (ставки категории).

**Extra-дисциплины (extra1/2/3)**: не участвуют в категорийном ценообразовании. Они текстовые, без FK, вне billing pipeline. Оставляем как есть.

## 1. Время, год, семестры

- `year` = календарный год, месяцы 1..12.
- Система оперирует **календарными годами** (2025, 2026...), но записи учеников отражают **учебные годы**:
  - **Полугодие 1** (месяцы 1–6) → второй семестр учебного года N-1/N
  - **Полугодие 2** (месяцы 7–12) → первый семестр учебного года N/N+1
- Для каждого `year` семестры: ровно 2, покрывают 12 месяцев без дыр/перекрытий; конфиг "граница" (последний месяц сем1), дефолт: 6.
- Изменение границы семестра разрешено **только для будущего года**, в котором ещё нет ни одной записи `KarteiRecord` (во избежание ретроспективного изменения истории).
- В записи ребёнка `subject1` (Сем.1) и `subject2` (Сем.2) — как правило, **разные дисциплины** (разные классы/группы), т.к. между полугодиями ребёнок переходит в следующий класс.
- Pricing engine работает **посеместрово по конфигу года**: для месяцев семестра 1 — по `subject1_ref` и её категории, для месяцев семестра 2 — по `subject2_ref` и её категории. Категории subject1 и subject2 могут быть разными (или одна с категорией, другая без).

## 2. Тип договора и "Gekündigt" — помесячно

### 2.1 Тип договора (yearly/monthly) — помесячная история

#### Модель `ContractTypeEntry`

| Поле | Тип | Описание |
|------|-----|----------|
| `record` | FK → KarteiRecord | Запись ученика |
| `effective_from_month` | PositiveSmallIntegerField (1-12) | С какого месяца действует |
| `is_monthly` | BooleanField | True = месячный контракт, False = годовой |
| `changed_by` | FK → User | Кто изменил |
| `changed_at` | DateTimeField (auto_now_add) | Когда изменил |
| `comment` | TextField (blank) | Комментарий |

**Unique**: `(record, effective_from_month)` — одна запись на месяц.

Тип договора в месяце M = последний `ContractTypeEntry` с `effective_from_month <= M` (упорядочен по `effective_from_month` DESC, берём первый).

**Дефолт для существующих записей**: если `ContractTypeEntry` нет — используется текущее значение `KarteiRecord.is_monthly_contract` для всех месяцев. Первый `ContractTypeEntry` создаётся, когда админ явно задаёт помесячную историю.

- Контрактов yearly и monthly примерно **50 на 50** в базе.

### 2.2 Статус активности (ACTIVE/PAUSED/TERMINATED)

В реальности возможны паузы и повторные заключения договора, поэтому статус активности должен быть помесячным.

#### Модель `ContractStatusEntry`

| Поле | Тип | Описание |
|------|-----|----------|
| `record` | FK → KarteiRecord | Запись ученика |
| `effective_from_month` | PositiveSmallIntegerField (1-12) | С какого месяца действует |
| `kind` | CharField (ACTIVE / PAUSED / TERMINATED) | ACTIVE = активен, PAUSED = пауза, TERMINATED = расторгнут |
| `changed_by` | FK → User | Кто изменил |
| `changed_at` | DateTimeField (auto_now_add) | Когда изменил |
| `comment` | TextField (blank) | Комментарий |

**Unique**: `(record, effective_from_month)` — одна запись на месяц.

Статус в месяце M = последний `ContractStatusEntry` с `effective_from_month <= M` (упорядочен по `effective_from_month` DESC, берём первый).

- ACTIVE → запись **считается активной** в месяце M (участвует в размере группы, может быть начисление).
- PAUSED → запись участвует в размере группы, но **не платит** в месяце M (начисление = 0.00).
- TERMINATED → запись **не участвует** в размере группы и **не платит** в месяце M (начисление = 0.00).

Для ясности:
- `counts_in_group_size(M)` = kind ∈ {ACTIVE, PAUSED}
- `is_billable(M)` = kind = ACTIVE

**Дефолт для существующих записей**: если `ContractStatusEntry` нет — считаем запись активной во всех месяцах, кроме случая, когда выставлено старое поле `contract_terminated_from_month`:
- если `contract_terminated_from_month` задан и `m >= contract_terminated_from_month` → статус TERMINATED,
- иначе → ACTIVE.

Если в записи существует хотя бы один `ContractStatusEntry`, то `contract_terminated_from_month` используется только как legacy-источник для первичной инициализации/фоллбэка и **не должен** влиять на дальнейшие расчёты (иначе нельзя корректно поддержать сценарии "TERMINATED → ACTIVE снова").

Правило приоритета: `ContractStatusEntry` определяет **сам факт начисления**. В месяцы `PAUSED/TERMINATED` итоговое начисление должно быть `0.00` **в любом режиме** (`months_mode=AUTO/LEGACY/OVERRIDE`), даже если вручную задан `month_*` (override).

`PAUSED` разрешён как для monthly, так и для yearly договоров. Тип договора продолжает учитываться помесячно для расчёта ставки в тех месяцах, где `kind=ACTIVE`.

## 3. Категории дисциплин (на год)

### Модель `SubjectCategory`

| Поле | Тип | Описание |
|------|-----|----------|
| `year` | PositiveSmallIntegerField | Календарный год |
| `name` | CharField | Название ("Русский", "Танцы", "Наххильфе"...) |
| `kind` | CharField (GROUP / INDIVIDUAL) | Тип категории |
| `yearly_rate` | DecimalField | Ставка €/UE (45 мин) для годичного контракта |
| `monthly_rate` | DecimalField | Ставка €/UE (45 мин) для месячного контракта |
| `group_threshold` | PositiveSmallIntegerField (default=6) | Порог малокомплектности (только для GROUP) |
| `is_active` | BooleanField | Мягкое удаление |

**Unique**: `(year, name)`.

### Модель `SubjectCategoryLink` (привязка дисциплины к категории)

| Поле | Тип | Описание |
|------|-----|----------|
| `subject` | FK → Subject | Дисциплина |
| `category` | FK → SubjectCategory | Категория |
| `year` | PositiveSmallIntegerField | Денормализовано из category для unique constraint |

**Unique**: `(subject, year)` — одна дисциплина может быть только в одной категории в данном году.

### Админские инструменты:

- CRUD категорий
- Привязка/отвязка дисциплин (перенос между категориями). При привязке к **GROUP**-категории — запросить месяц активации и начальную длительность (создать/настроить `DisciplineGroup` + `DurationEntry`)
- Удаление категории: **мягкое удаление** (`is_active=False`) + отвязка дисциплин
- Копирование категорий между годами (см. раздел 12)

### Дефолтные категории:

Создаются **автоматически при первом открытии** инструмента управления категориями в данном году. Если категории для года уже существуют — не создавать.

- Групповые: Русский, Немецкий, Английский, Шахматы, Танцы, Искусство, Наххильфе, Музыка, Логоритмика
- Индивидуальные: Наххильфе, Логопед, Индивидуальные занятия

## 4. Группы

### Модель `DisciplineGroup`

| Поле | Тип | Описание |
|------|-----|----------|
| `subject` | FK → Subject | Дисциплина |
| `year` | PositiveSmallIntegerField | Календарный год |
| `category` | FK → SubjectCategory | Категория (GROUP) |
| `auto_scaling_enabled` | BooleanField (default=False) | Включен ли автоскейлинг малокомплектных групп |

**Unique**: `(subject, year)`.

`DisciplineGroup` — годовой контейнер "Subject в рамках календарного года" для управления параметрами (длительность, ручной размер, автоскейлинг).
Фактическая активность и состав группы определяется **помесячно** по ссылкам из `KarteiRecord` (и может меняться на границе семестров и внутри семестра).

Автоматически создаётся при привязке Subject к **GROUP**-категории. Для INDIVIDUAL-категорий группа **не создаётся**.

При создании группы требуется задать начальную длительность (`DurationEntry`): дефолт 45 мин, **месяц активации выбирается вручную админом** (см. раздел 5).

### Важно: 1 Subject = 1 Group

Один Subject из групповой категории порождает ровно одну группу. Состав группы (какие дети в ней) определяется данными: какие `KarteiRecord` ссылаются на этот Subject через `subject1_ref`/`subject2_ref` в соответствующих месяцах. Чаще всего группа активна преимущественно в одном полугодии (но не обязательно).

### Будущее: инструмент "перевод между группами"

Отдельная будущая задача (не входит в первую итерацию): ручной инструмент для админа, который помогает переводить детей между группами при смене учебного года/класса.
Идея: админ выбирает исходную группу (например, "1A Klasse" в первом полугодии) и целевую группу (например, "2A Klasse" во втором полугодии) и применяет перевод к выбранным записям/месяцам (с учётом approvals).

## 5. Длительность — помесячная история

### Модель `DurationEntry`

| Поле | Тип | Описание |
|------|-----|----------|
| `group` | FK → DisciplineGroup | Группа |
| `effective_from_month` | PositiveSmallIntegerField (1-12) | С какого месяца действует |
| `duration_minutes` | PositiveSmallIntegerField | Продолжительность в минутах |
| `changed_by` | FK → User | Кто изменил |
| `changed_at` | DateTimeField (auto_now_add) | Когда изменил |
| `comment` | TextField (blank) | Комментарий |

Длительность в месяце M = последний `DurationEntry` с `effective_from_month <= M` (упорядочен по `effective_from_month` DESC, берём первый). Если записей нет — длительность не определена (нужно задать).

### Начальная длительность

При создании `DisciplineGroup` (обычно при привязке Subject к **GROUP**-категории) админ **вручную выбирает месяц активации** `T` (1..12).
Система создаёт начальный `DurationEntry` с:
- `duration_minutes = 45` (дефолт; можно изменить сразу)
- `effective_from_month = T` (выбранный месяц активации)

Система **не должна** пытаться угадать `T` по авто-размеру группы.

Если в каком-то месяце M есть хотя бы один ученик со статусом `ContractStatusEntry.kind=ACTIVE` (платит), но длительность для M не определена (нет ни одного `DurationEntry` с `effective_from_month <= M`) — в UI показывать ошибку/предупреждение и требовать задать длительность (например, добавить `DurationEntry` с более ранним `effective_from_month`).

### Перенос из прошлого года

При **копировании категорий из прошлого года** (раздел 12) длительности НЕ копируются. Но при создании нового `DurationEntry` в UI — **предлагать значение из последнего DurationEntry прошлого года** как дефолтное (если есть). Админ решает, менять или нет.

## 6. Размер группы — ручной/авто

### 6.1 Автоматический подсчёт (в реальном времени)

Для месяца M, для группы (Subject S, Year Y):

```
COUNT записей WHERE:
  year = Y
  AND (
    (semester(M, Y) = 1 AND subject1_ref = S AND месяц M активен в слоте Sem.1 по правилам start/end/csv)
    OR
    (semester(M, Y) = 2 AND subject2_ref = S AND месяц M активен в слоте Sem.2 по правилам start/end/csv)
  )
  AND запись НЕ TERMINATED в месяце M (ContractStatusEntry.kind IN (ACTIVE, PAUSED))
```

- Учитываются записи по полю `record.status`: Normal + Pending + Declined
- По `ContractStatusEntry.kind`: в размере группы участвуют ACTIVE+PAUSED; TERMINATED не участвует
- **Фоллбэк**: если `subject*_ref` не заполнен, сверять с `subject1`/`subject2` (нормализация: trim, collapse spaces, casefold)
- Для `status=PENDING`: для расчётов/превью использовать "pending-проекцию" tracked-части записи из `approvals.PendingChange.snapshot` (subject*_ref, start/end/csv, legacy subject и т.д.), чтобы размер группы отражал ожидаемое состояние после approval. Если не получается выразить одним SQL — допускается: базовый `COUNT` по текущим данным + точечная корректировка в Python на основе diff snapshot.
- ~1000 записей, ~200 дисциплин → подсчёт в реальном времени, без кеширования

#### Производительность

Подсчёт одной группы по `subject*_ref` — фильтрованный SQL `COUNT` по индексированным полям (PostgreSQL). Дополнительно возможна небольшая пост-обработка в Python для редких кейсов с legacy-фоллбэком и `PENDING` snapshot. Кеширование не требуется. Для массовых операций — `bulk_update` вместо поштучных save.

### 6.2 Ручной размер (override)

**Модель `GroupSizeEntry`**:

| Поле | Тип | Описание |
|------|-----|----------|
| `group` | FK → DisciplineGroup | Группа |
| `effective_from_month` | PositiveSmallIntegerField (1-12) | С какого месяца |
| `manual_size` | PositiveSmallIntegerField | Ручной размер |
| `changed_by` | FK → User | Кто |
| `changed_at` | DateTimeField | Когда |
| `comment` | TextField | Комментарий |

Если есть ручной override — он приоритетнее авто. Авто-размер **всегда показывается** рядом для справки.

Правило семестра: ручной override применяется **только** к месяцам того семестра, в котором находится `effective_from_month`.
Т.е. для месяца M ручной размер берём как последний `GroupSizeEntry` с `effective_from_month <= M` и `semester(effective_from_month, year) = semester(M, year)`.

### 6.3 Уведомления при расхождении

Когда вычисленный авто-размер для месяца отличается от того, что было использовано при последнем расчёте начислений — показывать **предупреждение в UI** группы. Это решает проблему "упущенных изменений" без автоматического пересчёта биллинга.

### 6.4 Фоллбэк по legacy subject

Для автоподсчёта обязательно учитывать фоллбэк на `subject1`/`subject2`, если `subject*_ref` не заполнен. Нормализация legacy subject: trim, collapse spaces, casefold.

## 7. Расчёт цены (GROUP) — помесячно

Итоговая цена = **"предлагаемая цена"** за ребёнка в месяц (НЕ записывается в `base_amounts` автоматически).

Для месяца M:

1. `contract_type` = тип договора записи в M (из ContractTypeEntry или fallback на is_monthly_contract)
2. `rate` = `category.monthly_rate` если monthly, иначе `category.yearly_rate`
3. `duration_coeff` = `duration_minutes(M) / 45` (дробные допустимы)
4. `base_price` = `rate × duration_coeff`
5. Если `auto_scaling_enabled` **И** `size(M) > 0` **И** `size(M) < threshold`:
   → `price = base_price × threshold / size(M)`
6. Иначе: `price = base_price`
7. Округление: CEILING до центов (действующее правило проекта)

`size(M)` считается по разделу 6 и включает `ContractStatusEntry.kind ∈ {ACTIVE, PAUSED}` (TERMINATED не входит). В UI дополнительно показывать `billable_count(M)` (только ACTIVE), чтобы было видно "сколько платящих".

Если `size(M) = 0` — автоскейлинг включить нельзя (цена = `base_price`). UI: включение `auto_scaling_enabled=True` запрещено, пока не существует ни одного месяца M с `size(M) > 0`.

## 8. INDIVIDUAL (Stundenfächer)

Для дисциплин с INDIVIDUAL-категорией:

- Если `ContractStatusEntry.kind` в месяце M ≠ ACTIVE (PAUSED/TERMINATED) → итоговая сумма в месяце = `0.00`
- Иначе сумма в месяце = `hours_amounts[M] × rate(contract_type_in_M)`
- `rate` берётся из категории (`yearly_rate` / `monthly_rate`)
- `contract_type_in_M` — из ContractTypeEntry или fallback на is_monthly_contract
- Без часов — суммы нет

UI-правило: в месяцы `PAUSED/TERMINATED` ввод `hours_amounts[M]` запрещён (read-only), чтобы избежать сценариев "ввели часы, но счёт всё равно 0". Если в будущем понадобится учёт часов без оплаты — делать отдельную фичу/поле.

Для **некатегорийных** INDIVIDUAL дисциплин — по-прежнему через `PriceOption` (вариант B).

## 9. Override цены группы — **ОТЛОЖЕН на Phase N+1**

Не реализуется в первой итерации. В будущем:

- Override = финальная цена €/Monat за ребёнка
- Раздельно yearly/monthly
- "С месяца X"
- Опасный режим + обязательное объяснение + подтверждение
- **Override проходит через Approval** — как и любое финансово значимое изменение. ADMIN/OPERATOR вносит override → PENDING → SUPERADMIN одобряет/отклоняет. (Текущий `MonthsOverrideView` уже работает именно так: вызывает `create_or_update_pending_change()`.)

## 10. Применение к base_amounts/month_*

### 10.1 Принцип: только по явному действию

Любые изменения параметров (длительность, размер, ставка, scaling, тип договора) меняют только **"предлагаемую цену"**. Запись в `base_amounts` / `month_*` — только по явному действию **"Применить с месяца X"**.

Исключение: изменения `ContractStatusEntry` (PAUSED/TERMINATED/ACTIVE) влияют на сам факт начисления и должны приводить к обнулению/пересчёту `month_*` в затронутых месяцах (через стандартный approvals-процесс, т.к. `month_*` — tracked fields).
Это правило сильнее `months_mode=OVERRIDE`: в `PAUSED/TERMINATED` месяцах нельзя выставить ненулевое `month_*`.

### 10.2 Режимы применения

**Поштучно** (на странице записи):
- Админ/оператор открыл запись → видит предлагаемую цену рядом с текущей → нажал "Применить с месяца X"
- Применение выполняется **в рамках выбранного слота/семестра** (Sem.1 или Sem.2) и только для месяцев, активных по правилам start/end/csv данного слота. Другой слот/семестр по умолчанию не трогается.
- Записывается в `base_amounts` для затронутых месяцев начиная с X, пересчитываются соответствующие `month_*` с учётом скидок
- Если запись в `months_mode=LEGACY` → действие "Применить" недоступно до конвертации в AUTO (через существующую кнопку/механику `Monate neu berechnen`)

**Массово** (на странице группы):
- Админ/оператор на экране группы → видит список записей с предлагаемыми/текущими ценами → нажал "Применить ко всем с месяца X"
- Bulk-обновление всех записей группы одной операцией (`bulk_update`)
- Перед массовым применением — подтверждение с превью (сколько записей затронется, какие цены изменятся)

### 10.3 Права доступа и Approval

**"Применить с месяца X"** изменяет `base_amounts` и `month_*` (начисления). Это финансово значимое действие → **всегда проходит через approval**.

| Роль | Действие "Применить цену" | Ограничение по месяцам | Результат |
|------|--------------------------|----------------------|-----------|
| **OPERATOR** | Создаёт PENDING → SUPERADMIN одобряет/отклоняет | Только текущий и будущие месяцы (`has_past_months_restrictions`) | Стандартный approval-поток |
| **ADMIN** | Создаёт PENDING → SUPERADMIN одобряет/отклоняет | Без ограничений — любые месяцы, включая прошедшие | Стандартный approval-поток |
| **SUPERADMIN** | **Не нажимает** "Применить цену" | — | Только одобряет/отклоняет PENDING |
| **USER** | Только просмотр предлагаемых цен | — | Read-only |

**Ограничение OPERATOR по прошедшим месяцам** — аналогично текущему поведению при редактировании записи: поле "С месяца X" для OPERATOR не может содержать прошедший месяц. Валидация через `get_allowed_months()` и `validate_past_months_restrictions()`.

**Массовое "Применить ко всем":**
- OPERATOR / ADMIN → создаёт PENDING для каждой затронутой записи → SUPERADMIN ревьюит пакетом
- SUPERADMIN при ревью видит сводку: сколько записей, какие цены, общая сумма изменений
- SUPERADMIN одобряет/отклоняет пакет целиком или поштучно

> **Принцип разделения ролей:** Бюро (ADMIN/OPERATOR) вносит изменения → Бухгалтерия (SUPERADMIN) одобряет. SUPERADMIN никогда сам не инициирует изменения данных — только утверждает или отклоняет предложенные.

## 11. Определение источника ценообразования (pricing source)

### Принцип: динамическое определение

Pricing source **НЕ хранится** на записи, а определяется динамически:

```
Для записи R, семестра S, месяца M:
  subject_ref = R.subject1_ref (если S=1) или R.subject2_ref (если S=2)

  Если subject_ref И SubjectCategoryLink.exists(subject=subject_ref, year=R.year):
    → CATEGORY (новая логика через ставки категории)
  Иначе:
    → PRICE_OPTION (старая логика через PriceOption / price*_ref)
```

### Обоснование:
- **Простота** — нет дополнительного поля для синхронизации
- **Консистентность** — всегда отражает актуальное состояние привязок
- **Безопасность** — уже записанные `base_amounts` сохраняются при отвязке дисциплины от категории; пересчёт пойдёт по PriceOption-пути только при следующем "Применить"

## 12. Копирование категорий между годами

### Что копируется:
- `SubjectCategory` (name, kind, yearly_rate, monthly_rate, group_threshold, is_active)
- `SubjectCategoryLink` (привязки дисциплин к категориям)

### Что НЕ копируется (специфично для года):
- `DisciplineGroup` — создаются заново при привязке Subject к GROUP-категории
- `DurationEntry` — не копируются; задаются заново в новом году с выбором месяца активации. В UI при создании первого `DurationEntry` **предлагать длительность из прошлого года** как дефолт
- `GroupSizeEntry` — ручные override'ы не копируются
- `ContractTypeEntry` — история типов договора специфична для года
- `ContractStatusEntry` — история активности специфична для года

### Логика:
1. Проверить, что в целевом году нет категорий (или предупредить о перезаписи)
2. Скопировать категории с привязками
3. Для каждого Subject в GROUP-категории — создать DisciplineGroup (если нет). `DurationEntry` автоматически не создавать, т.к. месяц активации выбирается вручную админом
4. Авто-подсчёт размеров и истории ContractTypeEntry/ContractStatusEntry — из данных целевого года

## 15. Сценарии и edge cases

### 15.1 Новый ученик — приходит среди года
1. Создаётся KarteiRecord с subject1_ref/subject2_ref
2. Авто-размер группы пересчитывается автоматически (реальное время)
3. Предлагаемая цена для группы может измениться (если скейлинг включён)
4. Применение новой цены — только по явному действию "Применить"

### 15.2 Ученик делает паузу / уходит (PAUSED/TERMINATED)
1. Админ добавляет `ContractStatusEntry(kind=PAUSED|TERMINATED, effective_from_month = T)`
2. Если `kind=PAUSED`: для месяцев `m >= T` запись **участвует** в размере группы, но начисление должно быть `0.00`
3. Если `kind=TERMINATED`: для месяцев `m >= T` запись **не участвует** в размере группы, начисление должно быть `0.00` (и это может повлиять на скейлинг/цену)
4. Пример: месяц 3 → 6 ACTIVE + 1 PAUSED ⇒ `size(3)=7`; месяц 4 → этот ученик TERMINATED ⇒ `size(4)=6`
5. Если ребёнок возвращается: добавить `ContractStatusEntry(kind=ACTIVE, effective_from_month = U)`

### 15.3 Перенос дисциплины между категориями
1. Админ отвязывает Subject от категории A, привязывает к категории B
2. DisciplineGroup обновляет ссылку на новую категорию (если GROUP→GROUP)
3. Ставки меняются → предлагаемая цена меняется
4. Уже записанные base_amounts не трогаются — изменения видны при следующем "Применить"

### 15.4 Отвязка дисциплины от категории
1. SubjectCategoryLink удаляется
2. DisciplineGroup деактивируется/удаляется
3. Pricing source переключается на PRICE_OPTION
4. Уже записанные base_amounts сохраняются
5. Если PriceOption не задан — предупреждение "Цена не определена"

### 15.5 Смена типа договора среди года
1. Админ создаёт `ContractTypeEntry(effective_from_month = T)` (например, monthly → yearly)
2. Предлагаемая цена для месяцев `m >= T` пересчитывается с `yearly_rate` (и наоборот, если yearly → monthly)
3. Применение — по явному действию

### 15.6 Два семестра — разные категории
1. Запись: subject1_ref = "Русский 1A" (GROUP, категория "Русский"), subject2_ref = "Русский 1Б" (GROUP, категория "Русский")
2. Или: subject1_ref в GROUP-категории, subject2_ref без категории (PriceOption)
3. Pricing engine обрабатывает каждый семестр **независимо**

### 15.7 Legacy записи (subject*_ref не заполнен)
1. Если `subject*_ref` не заполнен → категорийное ценообразование **не применяется** (pricing source = PRICE_OPTION).
2. Авто-подсчёт размера группы при этом может использовать фоллбэк на текстовое поле `subject1/subject2` (нормализация: trim, collapse spaces, casefold).
3. UI: явно помечать такие записи как **legacy** и показывать подсказку "Заполните subject*_ref, чтобы включить категорийный прайс и группы".
4. (UX-улучшение) Если нормализованное legacy-имя предмета однозначно совпадает с `catalog.Subject.name` и у этого Subject есть `SubjectCategoryLink` в данном году — показывать "возможное совпадение" и кнопку быстрого заполнения `subject*_ref` (с явным подтверждением админом).
5. Постепенная миграция: при редактировании записи оператор заполняет `subject*_ref` (и дальше запись начинает участвовать в новой логике прозрачно).

### 15.7.1 LEGACY months_mode (months_mode=LEGACY)
1. Если запись в `months_mode=LEGACY`, то действие "Применить" (категорийную/групповую цену в `base_amounts`) запрещено.
2. Предлагаемый путь: сначала конвертировать в `AUTO` через существующую механику `Monate neu berechnen`, затем применять цену с месяца X.

### 15.8 Взаимодействие с Approvals workflow

**Принцип**: Бюро (ADMIN/OPERATOR) инициирует изменения → Бухгалтерия (SUPERADMIN) одобряет. SUPERADMIN не вносит данные — только утверждает/отклоняет.

- Изменение subject*_ref → PENDING → SUPERADMIN одобряет/отклоняет (как сейчас)
- **"Применить цену"** (поштучно или массово) → **всегда PENDING** → SUPERADMIN одобряет/отклоняет
- Массовое "Применить ко всем" → создаёт PENDING для **каждой** затронутой записи
- SUPERADMIN при ревью массового применения видит **сводку**: сколько записей, какие цены, общая сумма
- SUPERADMIN может одобрить/отклонить пакет целиком или поштучно
- Изменение параметров категории (ставки, порог) — НЕ создаёт PENDING (это настройка "предлагаемой цены", без записи в base_amounts)
- (Опционально, для снижения числа approval-циклов) При смене предмета/группы в форме записи можно предлагать сразу задать "Применить цену с месяца X" и включать это в тот же `PendingChange`, чтобы SUPERADMIN одобрял перевод и перерасчёт начислений одним решением.

### 15.9 Совместимость со скидками (FamilyDiscount / RecordDiscount)

Новое категорийное ценообразование **не затрагивает** механизм скидок. Скидки работают на уровне `base_amounts` → `month_*`, независимо от источника base_amounts.

**Текущий pipeline (сохраняется без изменений):**

```
1. Источник base_amounts:
   ├── PriceOption (некатегорийные) — как сейчас
   └── Category pricing (новое) — rate × duration_coeff × scaling
                                    ↓
2. base_amounts записаны в JSON ({"month_1": "100.00", ...})
                                    ↓
3. calculate_month_values() — применяет скидки:
   a) Проверка: ContractStatusEntry (PAUSED/TERMINATED) → month = 0.00 (fallback: `contract_terminated_from_month`)
   b) Проверка: discounts_disabled / discounts_disabled_months
   c) Проверка: Nachhilfe → скидки НЕ применяются
   d) Сбор FamilyDiscount + RecordDiscount → percent_sum + fixed_sum
   e) after_percent = base × (1 - percent_sum)  [max 99%]
   f) after_fixed = after_percent - fixed_sum  [min 0.00]
   g) Округление CEILING → month_*
```

**Что НЕ меняется:**
- Формат `base_amounts` (dict str → Decimal) — остаётся прежним
- `calculate_month_values()` — вызывается как раньше, входные данные те же
- FamilyDiscount / RecordDiscount — модели и логика не трогаются
- Исключения (Nachhilfe, discounts_disabled) — работают как прежде
- Порядок применения (percent → fixed → clamp → round) — не меняется

**Что меняется (только источник base_amounts):**
- Для категорийных дисциплин base_amounts формирует **pricing engine** вместо PriceOption
- Промежуточный расчёт ("предлагаемая цена") → запись в base_amounts → далее всё как обычно
